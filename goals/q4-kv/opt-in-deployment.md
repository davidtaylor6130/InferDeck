# Qwen3.8 Radiance Q4 opt-in candidate

Status: **prepared, not deployed**. The current production service remains `0.9.0-alpha-55` on its existing active profile. This is a local experimental candidate, not a public release.

Its manifest pins the executable, active-profile YAML, embedded Python profile, INT4 overlay, two required kernel source/header files, both native DLLs and static assets by SHA-256. The executable reports `0.9.0-alpha-68 revision=2332e133f82a28c3b016afa16cc919e89e378f0c dirty=false`; executable SHA-256 is `77c8bab84495e82d70ac672383c0723439df602984b190f703e9b1eb131befd1`. The candidate active YAML SHA-256 is `f41e94924b2b56bd02d72fd0224fb8bb2aa16bd7595e0e40fac4c731f6ba68f5`. The packaged Python profile comes from the later local commit `2ef94a7` and SHA-256 `f7922e1dad9f34fcb22098faeab262d71c660f46cf9a48b9fc1308b9157c76b2`; the executable build revision remains the earlier alpha68 revision because C++ did not change.

Configure with `cmake -S . -B build -DINFERDECK_LOCAL_BUILD_NUMBER=68`, then build `inferdeck-gateway` in Release. `--version` and the repository's C++ unit/integration suite passed on the committed source: 148/148 tests. The changed Python profile passed 43/43 focused tests; raw result is `.UAM/AINotes/alpha68-tokenizer-serial-python-tests.txt`. The alpha68 executable with that exact profile loaded Qwen3.8 Q4 in isolated real InferDeck three times, returned coherent greetings, and passed four distinct concurrent HTTP-200 answers with four active slots. The frozen two-agent 64K+2K tool loop passed in 128.559 s with both exact answers, 63840 cached tokens per continuation, and 442 generated tokens. Raw evidence is `.UAM/AINotes/alpha68-tokenizer-serial-smoke-20260924T033612811Z.json`, its `.four-slots.json`, and `.UAM/AINotes/q4kv-64k2k-20260924T033717616Z-worker.json`. The prior profile took 128.786 s with the same 442 outputs; the 0.227 s single-run difference is noise. BF16/R4D median was 133.684 s with 1183 outputs, so the shorter Q4 task time does not establish faster compute. The original alpha55 production service and model were restored after each isolated run. Four-100K input-capacity and 100K answer-quality evidence remains from alpha67, not alpha68.

Alpha67's frozen two-agent 64K+2K tool-loop times were 137.930 and 136.871 seconds versus the BF16/R4D 133.684-second median. Its four simultaneous cold inputs each contained 100194 tokens and returned HTTP 200, but two answers reached the explicitly requested 256-token output cap. A separate 100K tool continuation completed normally with exact `read_file` and `BUILD_TAG` checks, 100320 cached tokens, and 99.074 seconds from first send to final answer. These results support an opt-in trial, not a claim of higher raw PP or complete long-term stability.

The earlier 29557.65625 MiB post-batch reading is GPU-wide VRAM used from `windows_pdh_dxgi`. A later Windows per-process dedicated counter measured idle Q4 Radiance at 27559.316 MiB and Vulkan Qwen3.8 at 26914.594 MiB on the same R9700, Q4 +644.722 MiB (+2.4%); raw result is `.UAM/AINotes/alpha68-process-vram-20260924T031947264Z.json`. Dedicated-VRAM parity under comparable load remains open.

The package's `config/gateway.active.optin.yml` preserves every existing active-profile byte and inserts one model before `model_aliases:`. Its new ID is `qwen3.8-27b-radiance-q4`, with four fixed 106496-token slots, `r4d_int4`, `int4_per_token_head` KV and text-only capability. The existing one-slot BF16 `qwen3.8-27b-radiance`, default, aliases and Vulkan `qwen3.8-27b` with `mmproj_path`/vision remain unchanged. Select Q4 explicitly by its new ID.

Run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .UAM/AINotes/Deploy-Alpha68Q4OptIn.ps1` for the **read-only** preflight. ## Activation and rollback

Before activation, confirm the current live active/base config and executable hashes still match `manifest.json`, the `InferDeck` NSSM target is `C:\InferDeck\inferdeck-gateway.exe -c config\gateway.yml`, the active profile is in use, the service has no active/queued requests, and every package artifact matches its manifest. Back up the live executable, active config, Python profile and any files at the new overlay/kernel/DLL destinations under `C:\InferDeck\backups\` before stopping the service. Keep the base config untouched. The package's static assets and all 24 root DLLs matched production by SHA-256 when prepared; verify this again and leave them unchanged if they still match.

After stopping only `InferDeck`, copy the alpha68 executable, candidate active YAML, Python profile, INT4 overlay, two required kernel source/header files and two hash-pinned DLLs to their `C:\InferDeck` destinations. Start the service and verify the reported alpha68 revision, active profile, model inventory and a real Q4 chat request. Swap back to the pre-deployment model and confirm it serves. If any step fails, stop the service, restore the backed-up executable/active YAML/Python profile and all touched files, restart, and verify the original model. Retain the backup and raw validation record. Do not change existing aliases or switch the default to Q4.

The local deploy helper backs up the eight touched destinations and starts an independent hidden watchdog before stopping the service. Adversarial review found and we fixed a hash-check race, a watchdog deadline shorter than the longest validation path, a missed stop-timeout rollback, unbounded rollback paths, and a watchdog activation-before-start case. The reviewed helper now checks live and backup hashes again immediately before activation, restricts rollback to the eight destinations, and uses parent-process monitoring plus an 1800-second ceiling. It also suppresses PowerShell's unsupported `Expect: 100-continue` header when issuing control POSTs. These safeguards have passed parser validation and read-only preflight; live rollback has not been exercised on alpha68.

The candidate still references the existing local Python/ROCm/vLLM/Radiance environment and model artifact under `build/runtime-radiance-probe`; those large dependencies are **not** bundled. Do not clear or move that tree while Radiance is configured. LocalSystem access and the final alpha68 service-switch path remain to be validated live. Upstream source authorship/licensing for the native INT4 copy remains unresolved, so do not publish this package or source as a release.

Windows Application events 85300 and 86004 recorded intermittent native `tokenizers.pyd` access violations at the same offset during BF16 and Q4 cold loads. Three clean changed-profile Q4 loads do not prove the mitigation fixed it; the stability gate remains FAIL. The original goal's repeated 20-cycle/100-mixed-request reliability gates and complete four-agent 100K answers are also open. Keep the candidate opt-in and the proven BF16/Vulkan paths available while those are assessed. Q4 Radiance is text-only; Vulkan Qwen3.8 retains its configured vision projector.
